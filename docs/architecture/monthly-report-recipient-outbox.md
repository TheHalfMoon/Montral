# Monthly report recipient outbox — staged dispatcher, production activation NOT implemented

## Existing contract and remaining gap

`workspace_setting.last_report_month` atomically claims an entire workspace-month, and `sendMonthlyReports` makes one best-effort email attempt per eligible owner. Errors **before** any provider request can reopen the month; errors **after** a provider request are intentionally never automatically retried because acceptance is ambiguous. A durable per-owner PostgreSQL foundation, atomic quota claim, and **staged internal dispatcher** now exist. The staged dispatcher is NOT connected to the active monthly report sender, scheduler, routes or background recovery. The staged atomic owner snapshot and restart discovery now close the **new-path pre-recipient crash gap**, but cannot safely recover **legacy org-only claims** with unknown mail history. There is no production recovery scheduler or recipient-level reconciliation API. Do not describe this feature as implemented or production-qualified.

The pre-send mail-render preflight in `apps/api/src/reports.ts` ensures that a corrupt component or contact cannot cause a halfway send or charge before all messages have been rendered. It is a narrow prerequisite, not an outbox substitute.

## Implemented and remaining safety rules

The PostgreSQL migration `0041_same_millenium_guard` and repository methods implement the composite recipient key, owner/month validation, immutable reservation, atomic first-attempt claim and terminal result transition. The Montral edition also has a **single-transaction** quota+outbox claim function. An isolated dispatcher now exercises these methods with real PostgreSQL and a synthetic mail transport, but **no scheduled or deployed dispatcher** exists. See [staged-dispatcher evidence](../evidence/2026-10-31-staged-monthly-outbox-dispatcher.md). They are **staged only**, not invoked by the production report sender. The remaining requirements below describe what must be integrated before activation.

1. **Foundation implemented, sender integration outstanding:** a dedicated outbox with a **unique `(organization_id, report_month, recipient_user_id)`** key; reference existing org/user rows for deletion rules, store the planned recipient email/locale and a minimal immutable report snapshot or content hash, `state` (`prepared`, `attempted`, `accepted`, `uncertain`, `skipped`), monotonic attempt marker and timestamps. Do not persist SMTP credentials, unsubscribe tokens or full provider exception strings. Confirm how to handle email changes after claim.
2. **Staged atomic materialization implemented, production integration outstanding:** `claimMonthlyReportsWithRecipients` takes a workspace-setting row lock, snapshots all currently authorized owners and updates `last_report_month` within one PostgreSQL transaction. `recoverPreparedMonthlyReportWorkspaces` only revisits committed `prepared` rows; a staged batch orchestrator can resume them after a simulated crash. Historic org-only claims are **not** assumed safe to resend. An explicit safe transition from the legacy scheduled worker to the staged worker, plus real kill/crash testing and snapshot-content policy, remain required. [Evidence](../evidence/2026-10-31-atomic-monthly-materialization-recovery.md).
3. **Idempotent quota reservation implemented and the staged SQL claim now couples it to recipient state, production integration outstanding:** `montral_usage_reservation`, `montral_spend_usage_once`, and optional metered `reserveEmailQuotaOnce(org,key)` prevent double charge per tenant/accounting-month/recipient idempotency key while serializing against legacy email spenders. They return a separate `newlyReserved` marker so a replayed grant cannot authorize a duplicate send. The optional staged `montral_claim_monthly_report_send` now couples the booking and the outbox phase within one database transaction, but it is **not invoked by the production sender**. Existing `spendEmails(org,count)` remains non-idempotent for this purpose and is still used by the active monthly sender. Do not enable the outbox on these primitives alone. [Qualification](../evidence/2026-10-31-idempotent-email-quota-reservation.md).
4. **Atomic quota+outbox claim now implemented but SMTP integration outstanding:** The staged `montral_claim_monthly_report_send` takes a row lock on a prepared monthly recipient, validates owner/email/report status and period, and uses the same PostgreSQL transaction to reserve the deterministic email quota key and transition to `attempted` (fresh grant), `skipped` (denied), or `uncertain` (prior reservation with unknown dispatch history). Rollbacks undo all three changes. It is exposed through optional metered `claimMonthlyOutboxAttempt` and **not called by the current sender**. After an attempted SMTP request, never automatically replay `attempted` or `uncertain`. Mark `accepted` only on verified success and reconcile ambiguous outcomes. There is no generic exactly-once guarantee in SMTP. [Evidence](../evidence/2026-10-31-atomic-monthly-outbox-quota-claim.md).
5. Continue sending other recipients/workspaces independently. If entitlement service, policy or snapshot preparation fails before a recipient is marked attempted, release only the safe, unattempted work. Keep business rules (opt-in, disabled reports, first three UTC days, quotas) unchanged.
6. **Staged internal owner-only reconciliation now implemented; authenticated operator surface still outstanding:** the additive `0042` audit table persists at most one owner-attested `provider_accepted` or `unresolved` decision with a hashed reference and scoped aggregate counts. The API rejects non-owner workspace actors, blocks decisions on recent in-flight attempts, and never requeues an SMTP attempt. **It has no identity authentication, no HTTP/dashboard integration, and does not verify external provider evidence.** A future operator interface must authenticate the caller, ensure evidence is genuine, establish retention and privacy controls, and never permit automatic retry. [Evidence](../evidence/2026-10-31-staged-monthly-reconciliation.md).

## Must-pass qualification before enabling the outbox

- PostgreSQL concurrent claiming and uniqueness (multiple workers); transaction rollback and migration replay on an *existing* database.
- Kill process after org claim but before enqueue; after enqueue but before quota reservation; after quota reservation but before provider call; after provider acceptance but before recorded success. Reconcile credits and ensure no duplicate external messages.
- Owner removed, email changed, report disabled, month rolled over during worker downtime, partial allowance, invalid grant and transient database outage; securely erase deleted workspace's outbox.
- Real local SMTP acceptance/delay/timeout with synthetic inbox, plus hosted CI, load tests, and external-provider reconciliation prior to release. Separate a live merchant quota metering test from local simulations.

**Release decision: NOT READY — staged internal dispatcher only, no live/scheduled outbox dispatch.** Do not use the design document to turn any product or release gate green. No paid service, real email delivery, public deployment or production billing is authorized by this document.
