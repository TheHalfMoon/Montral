# Staged once-frozen monthly report content — 2026-10-31

**Scope:** PRIVATE `TheHalfMoon/Montral`, authorized Mac, synthetic PostgreSQL and local SMTP only. **Not a production scheduler integration, no cloud deployment or external email.**

## Previous gap

The staged outbox already persists immutable recipient contacts/locale per workspace-month and claims each SMTP attempt with idempotent quota. However, `dispatchPreparedMonthlyOutbox` previously queried current workspace name, monitor history and incident summaries afresh on **every invocation**. If a worker stopped after delivering the first recipient, then restarted after a monitoring data change, the next recipient could receive materially different values for the *same report month*. A current report recomputation is not evidence that it equals content previously accepted by a provider.

## Implemented staged storage contract

- Additive Drizzle migration **`0043_unknown_dagger`** creates `monthly_report_content`, uniquely scoped to `(organization_id, report_month)`, containing a workspace-name snapshot, a typed JSONB list of monthly monitor statistics and a created timestamp. Strict month, nonempty name and nonempty JSON-array constraints apply. The table is scoped by workspace FK and is deleted on workspace deletion. Monitor names/statistics are **confidential** and must not be logged, included in exposed HTTP responses or treated as public telemetry.
- A database-level `BEFORE UPDATE` trigger **rejects all modification** after a row is inserted, including SQL changes that bypass the repository. `INSERT ON CONFLICT DO NOTHING` prevents concurrent workers from replacing the first committed version. Deletion for privacy/workspace erasure remains permitted.
- New internal `Repo.monthlyReportFrozenContent` reads only the particular organization/month; `Repo.freezeMonthlyReportContent` validates content and a 128 KiB UTF-8 payload bound, locks the workspace settings row, checks reporting opt-in and the exact claimed month, and requires **at least one `prepared` recipient and zero previously attempted/decided recipients** when creating a fresh snapshot. It commits the content once, or returns the prior committed version. The DB transaction does not send SMTP, consume quota or alter the recipient state. An invalid, absent, mismatched or stale month fails closed.
- The **staged-only** dispatcher first reads the existing frozen version. If absent, it fetches current metrics, attempts to freeze once, and **returns without sending or claiming quota** if freezing is denied or fails. Once a version exists, it renders all subsequent recipients—including after a restart—from that same persisted data, never re-reading current metrics for rendering. A pre-existing `attempted` row without a frozen version is intentionally not backfilled, because its historical content is unknown and re-snapshotting would be misleading. Such records require explicit independent reconciliation.
- `sendMonthlyReports`, the production legacy scheduler, and the default-disabled operator review are unchanged. There is **no activation flag** linking staged dispatch to cron. This fixes per-month content drift **after the first frozen version is committed**, not content differences that may have existed in legacy mails. The report may include aggregated private monitors; data-retention/erasure policy for historical report snapshots is not yet approved.

## Regression and fault evidence

New real PostgreSQL + synthetic SMTP tests verify: first recipient accepted, metrics/workspace name mutated before the second recipient, second message still uses the exact original snapshot; freeze cannot be recreated when a previous recipient was already attempted without a snapshot; eight concurrent frozen-content writers converge on one committed version; invalid report components cannot be frozen or charged; and an explicit SQL `UPDATE` is rejected by the database trigger while deleting the workspace cascades to erase the snapshot. The earlier staged batch-recovery, multiworker, quota, provider-timeout, uncertain-result and real local OS `SIGKILL` cases remain part of full qualification. An updated historical database migration test upgrades the **0040 schema through 0041, 0042 and 0043** and verifies old claimed months are not resurrected. The PostgreSQL dump/restore drill now verifies the new table and immutability trigger function after restore.

## Remaining production NO-GO conditions

A snapshot freezes **only after recipient materialization, before the first SMTP claim**, not necessarily exactly at UTC month end. It does not guarantee that historical rollups are complete, define a retention policy for confidential report content, independently verify provider delivery, or address external SMTP outages and hosted PostgreSQL failover. Production cron remains on the legacy sender, and the staged worker is deliberately never activated. A safe migration requires every old scheduler to be quiesced, existing ambiguous attempts reconciled without replay, real external-provider qualification, managed backup/PITR, hosted CI and independent security/privacy approval. No publish, deploy, paid services, real mail or active scheduler switch is authorized by this local work.
