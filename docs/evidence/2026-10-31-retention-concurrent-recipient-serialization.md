# Monthly frozen-content retention: concurrent recipient safety — local synthetic qualification

**Date:** 2026-10-31 (Asia/Riyadh). **Repository:** PRIVATE `TheHalfMoon/Montral`. **Scope:** isolated, disposable synthetic PostgreSQL on authorized Mac. **Release remains NO-GO.** No production cleanup schedule, retention policy, mail dispatch, customer-data deletion, or deployment was activated.

## Failure reproduced before the fix

The staged, localhost-and-synthetic-marker-guarded `purgeFrozenContentInDisposableTestDb` previously checked recipient eligibility with `EXISTS` and `NOT EXISTS` in one READ COMMITTED SQL statement. It locked `monthly_report_content`, but **not** `monthly_report_recipient`. PostgreSQL can read the last committed version of a recipient while an unrelated transaction is updating that recipient but has not yet committed. A concurrent status change to `uncertain` therefore did not stop a snapshot deletion decided from stale `accepted`/`skipped` states.

A new real-PostgreSQL regression began a writer transaction, changed two synthetic terminal recipients to `uncertain`, held the transaction open, then launched the retention deletion before releasing the writer. On the original code, the purge **deleted 2 confidential snapshots instead of 0**, demonstrating the race rather than assuming an issue from inspection alone. The following test also failed because its fixture had been wrongly deleted.

## Fail-closed correction

After validating the real local PostgreSQL server and an explicit per-database synthetic fixture marker, the rehearsal transaction now takes `LOCK TABLE monthly_report_recipient IN SHARE MODE` with a 3-second transaction-local lock timeout, **before** selecting/deleting candidates. This lock conflicts with SQL writes to the recipient table, waits for any in-flight writer to commit/roll back, and prevents new writes until the bounded deletion transaction commits. The subsequent DELETE statement sees the committed state in READ COMMITTED, so it cannot use an uncommitted stale version of the recipient to decide eligibility. If a lock cannot be obtained within the bound, the transaction aborts without deletion. The test restores the synthetic terminal fixture after the race to validate that ordinary eligible synthetic snapshots can still be removed. A separate regression deliberately holds a writer beyond the 3-second lock timeout and verifies PostgreSQL code `55P03` with all seven snapshots intact; contention never becomes permission to delete.

The table-wide lock is **intentionally conservative and unsuitable for production use**: it can briefly block recipient writes. It is acceptable only in this already-disposable, explicitly marked, manual test-only destructive rehearsal. A future production purge requires a separately reviewed coordination design, privacy/retention policy, service-level lock/concurrency budget, verified provider evidence and explicit rollout authorization.
