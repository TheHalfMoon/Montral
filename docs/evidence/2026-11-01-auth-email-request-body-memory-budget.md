# Authentication email-quota request body memory ceiling

**Date:** 2026-11-01 Asia/Riyadh. **Scope:** private Montral; synthetic account and oversized request fixtures on macOS with supported Node, disposable local PostgreSQL; no real accounts, remote auth provider, customer data, release or deployment.

## RED: unbounded body materialization before per-email rate limiting

The API intercepts public Better Auth paths (`sign-in/email`, `sign-up/email`, `request-password-reset`, `forget-password`, `send-verification-email`) to enforce a PostgreSQL-backed shared IP quota and per-email limit. Before forwarding to Better Auth, it called `c.req.raw.clone().json()` on the **entire untrusted request body**. This buffers any body size before the email's 254-character key limit is checked; the per-IP quota counts attempts but cannot cap memory consumed by any one attempt. An in-process regression with 32 KiB of synthetic signup JSON reproduced the old unbounded parse: **RED**, returned an extracted email instead of rejecting the oversized request. The original API code directly used this unbounded parsing operation.

## Narrow bound and preserved behavior

`limitedAuthBody()` now reads a clone of the body as a stream with a strict **16,384-byte** budget. It checks declared `Content-Length` for a fast rejection but also counts actual received bytes, so an inaccurate or missing length cannot bypass it. On overflow, it rejects HTTP **413** `{error: "Payload too large"}` before handing the body to the auth provider or continuing email-key processing, and requests cancellation of both stream branches without blocking on a possibly unending sender. A bounded valid body is decoded and parsed to extract the same email; malformed small JSON is still forwarded to Better Auth to handle in the established way. The original body remains readable for the downstream auth handler after a normal request. The database-backed shared and per-email rate-limit counts, key normalization, API response for ordinary auth requests and sign-in credentials were not changed.

**GREEN:** four direct helper regressions (oversized 32-KiB JSON, intentionally falsely short `Content-Length` on streaming body, explicitly oversized declared length rejected without buffering, valid body preserved for downstream) and four real-PostgreSQL API hardening cases PASS. The new real endpoint check asserts 413 on an oversized signup body; existing signup and per-email login/sign-up rate-limit regressions still pass. The tests are local and bounded and do not send unbounded traffic to any public provider.
