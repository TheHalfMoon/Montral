# Webhook Inbox creation: bounded JSON body before any credential creation

**Date:** 2026-11-01 Asia/Riyadh. **Scope:** private Montral, deterministic local simulated requests on macOS, synthetic accounts and disposable PostgreSQL. No public deployment, real customer events, paid services or external webhooks.

## Reproduced bounded-input gap

Private `POST /api/hooks/inboxes` is restricted to workspace managers, and a valid inbox name is at most 100 characters. The handler nonetheless used `c.req.json()` to parse **all** supplied JSON bytes before applying its Zod schema. A sufficiently large authenticated request could allocate unbounded memory even though only a short name is needed. The first new regression submitted an 8-KiB JSON body with `name: "test"` plus unexpected padding. **RED:** the original handler returned HTTP 400 only after reading/parsing the entire body; it did not return a size-specific HTTP 413. No inbox was created because the strict Zod schema rejected the unexpected field, but memory use was not bounded by it.

## Fix and properties

`readInboxCreation()` now caps the actual stream at **4,096 bytes**, uses a fast `Content-Length` check where present but **does not trust** a forged shorter length, rejects oversized input with HTTP **413** `{error: "Payload too large"}` before Zod validation or secret-token generation, and returns HTTP 400 for invalid short JSON as before. Requests with no body continue through the normal invalid-name validation. On overflow, the code requests cancellation without waiting for an uncooperative producer, releases the reader lock, and never reaches `montral_create_hook_inbox` or allocates the one-time receiver token. Bounded JSON is UTF-8 decoded with fatal decoding; malformed input does not trigger a server 500.

The new tests in `montral-hooks.test.ts` cover finite 8-KiB JSON, a deliberately false `Content-Length: 5` on the same oversized body, and a never-ending 2-KiB-chunk stream whose `cancel` callback deliberately never resolves: all must promptly receive HTTP 413 with `private, no-store`, `no-referrer`, `nosniff` and `noindex` response headers and **zero** inbox writes. Previously existing valid creation, hashed secret, tenant/project scope, manager permission and receiver body-size cases remain unchanged. Focused **12/12 PASS** after the fix.
