# Single sign-on with OpenID Connect

## Gap
Montral signed people in with email and password (optionally with TOTP) or
with GitHub. Teams could not use their own identity provider, could not
provision members from it, and could not make it the only way into a
workspace (task ledger item 14, gap matrix "SSO (OIDC/SAML)").

## Scope
- **Per-workspace connections** (`sso_connection`, migration `0054_oidc_sso`),
  at most one per workspace, managed by the workspace **owner** from a
  signed-in session (`GET/PUT/DELETE /api/sso`, `POST /api/sso/test`,
  `POST /api/sso/domains/:domain/verify`). Admins, members, API keys and
  OAuth agents get 403. The fields are the issuer, the client id, the client
  secret (write-only), the email domains, the role for people provisioned on
  their first sign-in (`member` or `admin`, never `owner`), "require SSO" and
  enabled.
- **Verified domains** (`sso_domain`). Each domain gets a random TXT value
  at `_montral-challenge.<domain>`, checked with the resolver that status
  page custom domains already use (`verifyDomainToken`). Workers have no
  resolver API, so they use DNS over HTTPS there. A partial unique index
  lets only one connection on the instance hold a verified domain. Only
  verified domains route sign-ins (`email` → connection), provision people
  or match existing links.
- **Instance-wide provider** for self-hosters: `OIDC_ISSUER`,
  `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` (all three, or none) and optionally
  `OIDC_ALLOWED_DOMAINS`. Its first sign-ins create an ordinary account with
  a personal workspace and follow `DISABLE_SIGNUP` (a pending invitation
  still lets the person in). The variables are documented in
  `.env.docker.example`, `.env.example` and `docker-compose.yml`, and the
  env-docs guard test checks that those files stay consistent.
- **Sign-in** is a Better Auth plugin (`apps/api/src/sso-auth.ts`), so a
  successful SSO sign-in gets an ordinary Montral session (same cookie,
  expiry, hooks and sign-out):
  - `POST /api/auth/sso/start` takes a work email, a workspace slug or
    `intent: "link"`, and returns the provider's authorization URL.
  - `GET /api/auth/sso/callback` is the only redirect URI. It is built from
    `BETTER_AUTH_URL` and never taken from a request.
- **UI**: the sign-in page has a "Sign in with SSO" button (shown when a
  provider exists) that asks for a work email or workspace ID, and explains
  `?sso_error=` codes. When a password sign-in is refused for SSO_REQUIRED,
  the page opens the SSO panel for the same address. The Settings page has
  an owner-only "Single sign-on (OpenID Connect)" card: redirect URI,
  issuer, client id, write-only secret, domains with their TXT records and a
  Verify button, role, enabled, require SSO, Test connection and Delete.
  Account has a "Single sign-on" card with "Link single sign-on". All strings
  have English and Simplified Chinese versions.
- **Docs**: `/docs/self-host#sso` (en and zh) covers a generic provider,
  plus text-only examples for Keycloak, Authentik, Entra ID, Google
  Workspace and Okta, the linking policy, require-SSO and break-glass, and
  the security notes. `/docs/api#sso` (en and zh) covers the endpoints,
  errors and audit actions. There is also a changelog entry.

## Library decision
- Better Auth 1.7.7 (installed) ships `genericOAuth`. Montral does not use it:
  - Its providers are fixed when the auth object is built. Montral needs
    per-workspace connections from the database.
  - It fetches discovery and JWKS with plain `fetch` / `createRemoteJWKSet`,
    which bypasses `netguard.ts` (no SSRF guard, no private-address
    refusal, no address pinning).
  - Its account-linking rules are global (`accountLinking`), so the stricter
    SSO policy below could not apply to SSO alone.
- `@better-auth/sso` is not installed. It would add a dependency tree that
  includes SAML (samlify and its XML stack, see below) and still has global
  linking and unguarded fetches.
- The relying party is therefore Montral code (`apps/api/src/sso-oidc.ts`)
  built on **`jose` 6.2.12**, which is already a pinned dependency of the
  API. `jose` does all JWT/JWS parsing and signature checking
  (`jwtVerify`, `createLocalJWKSet`, `decodeProtectedHeader`). No JWT
  cryptography is written by hand. **No new dependency** was added, and the
  lockfile is unchanged.

## Security design
- **Flow**: authorization code with PKCE `S256`, `state` and `nonce`, each
  32 random bytes. Discovery must advertise `code`, and `S256` if it lists
  PKCE methods at all.
- **State storage**: the pending sign-in (`sso_flow`) is keyed by
  SHA-256(state). The raw state is never stored. Each flow carries:
  - the SHA-256 of a **browser binding** secret. That secret lives in an
    HttpOnly, SameSite=Lax cookie, which is `__Host-montral_sso_flow` over
    https, so a sibling subdomain cannot toss one in;
  - the nonce, the PKCE verifier, the intent, the return path (a relative
    path inside the app only) and a 10-minute expiry.
- **Single use**: the callback consumes the flow with
  `DELETE … WHERE state_hash = $1 AND binding_hash = $2 RETURNING`. A
  replayed state, an expired one, or a state presented by another browser
  finds nothing. A wrong browser does not consume the flow, so the rightful
  browser can still finish.
- **Token request**: `client_secret_basic` (form-encoded per RFC 6749
  §2.3.1) or `client_secret_post`, whichever discovery offers. The redirect
  URI and verifier go with it. Montral uses only the id_token. Access and
  refresh tokens are not stored.
- **id_token** (OIDC Core §3.1.3.7):
  - Algorithms are restricted to RS256/384/512, PS256/384/512,
    ES256/384/512 and EdDSA, intersected with what discovery offers. `none`
    and every HMAC algorithm are refused before key lookup, so a provider's
    public key can never be used as an HMAC secret.
  - Keys come from the provider's JWKS, keeping only public signing keys:
    `kty` RSA/EC/OKP, `use` absent or `sig`, no `d`, `p`, `q`, … or `k`.
  - `iss` must equal the configured issuer exactly. Discovery's `issuer`
    must also equal it exactly (Discovery §4.3).
  - `aud` must contain the client id. With several audiences `azp` is
    required, and when present `azp` must equal the client id.
  - `exp`, `nbf` and `iat` are checked with 60 s skew. A token issued more
    than 10 minutes ago is refused, and so is one issued in the future.
  - The nonce is compared in constant time. `sub` is required (at most 255
    characters).
  - The RFC 9207 `iss` response parameter is checked when present (mix-up
    defence).
- **Key rotation**: discovery and the JWKS are cached for 10 minutes per
  isolate. An unknown `kid` refetches the JWKS, at most once per 30 s per
  provider, so a burst of unknown kids cannot make the server hammer the
  provider. A key set with several matching keys and no `kid` has each
  candidate tried, at most ten.
- **SSRF and resource bounds**: every request to the provider (discovery,
  JWKS, token) goes through `guardedFetch(…, { follow: false, publicOnly:
  true })`. That means:
  - public addresses only, connections pinned to the validated addresses,
    and no redirects;
  - an 8 s deadline covering the headers and the body;
  - a 64 KiB cap on the response (checked against Content-Length and the
    bytes actually read).
  `ALLOW_PRIVATE_TARGETS` (monitors) does **not** open this path. A
  provider on a private network, or over plain http, needs the separate
  opt-in `SSO_ALLOW_PRIVATE_IDP=true`. That opt-in does not switch the guard
  off (`privateTargetFetch` in `netguard.ts`): private, loopback and
  internal names become reachable, but every address the host resolves to
  is still checked against `addressAlwaysForbidden`, the connection is
  pinned to those addresses, and redirects, the deadline and the byte cap
  stay. `addressAlwaysForbidden` covers link-local and metadata (169.254.0.0/16,
  fe80::/10, 100.100.100.200, fd00:ec2::254), multicast and reserved
  (224.0.0.0 and up, ff00::/8), 0.0.0.0/8 and `::`, also when embedded in
  IPv6 (mapped, compatible, NAT64, 6to4). Endpoint URLs from discovery must
  be https (or http under that opt-in) and must not carry credentials or a
  fragment.
- **Secret binding**: the client secret is entered for one issuer and one
  client id. Changing either needs the secret again (`400 secret_required`).
  When a secret is entered, the token endpoint that discovery names at that
  moment is stored (`sso_connection.token_endpoint`). A sign-in sends the
  secret only there: if discovery later names another token endpoint, the
  sign-in stops before any request (`connection_misconfigured`) until the
  owner saves the secret again.
- **Client secret at rest**: AES-256-GCM via WebCrypto. The key is derived
  with HKDF-SHA-256 from `BETTER_AUTH_SECRET` (salt
  `montral-sso-client-secret`, info `v1`). The connection id is the
  additional authenticated data, so a ciphertext copied into another row
  does not decrypt. The secret is never returned (`hasClientSecret: true`
  only), never logged and never audited (the audit log keeps the field
  name `clientSecret`, never the value). If `BETTER_AUTH_SECRET` changes,
  sign-in fails closed with `connection_misconfigured`.
- **Errors and logs**: every failure redirects to
  `/login?sso_error=<code>`, or `/app/account?sso_error=<code>` for a link,
  with a fixed code. Server logs carry only a class (`SSO sign-in refused
  (invalid_id_token); private diagnostics suppressed`). The provider's
  `error_description`, tokens and codes are never logged.
- **Rate limits**: `/api/auth/sso/start` and the callback are counted per
  client address (30 per 10 minutes, or a shared 450 without a trusted
  proxy), like password sign-in. Discovery tests and domain verification
  have a per-workspace budget.

## Linking and provisioning policy
1. An identity is keyed on **(connection, issuer, subject)**: Better Auth
   `account` rows with `provider_id = "sso:<connection id>"` and
   `account_id = "<issuer>|<sub>"`, under a partial unique index. Changing
   a connection's issuer removes its links, which could never match again.
2. The provider must assert `email_verified === true` (the boolean, not
   `"true"`), and the email's domain must be a verified domain of the
   connection (or in `OIDC_ALLOWED_DOMAINS` for the instance provider).
   Otherwise the sign-in is refused, with no override.
3. A linked identity signs in its user.
4. An unlinked identity whose email **no Montral user has** is provisioned
   just in time. The user, the link and the membership (the connection's
   workspace only, with the default role) are created in **one SQL
   statement**. The new user's email is marked verified and the user has
   no password. A concurrent duplicate loses on the unique constraints and
   re-reads the winner.
5. An unlinked identity whose email **already belongs to a Montral user is
   refused** (`link_required`). An email match never links. Otherwise a
   workspace owner who controls an identity provider, or a compromised
   provider, could take over any existing account with an address in the
   verified domain, including that account's other workspaces. The account
   holder links instead:
   - sign in the usual way (password + 2FA, or GitHub), which proves they
     hold the Montral account;
   - open Account → Single sign-on → Link
     (`POST /api/auth/sso/start {intent:"link"}` needs the session);
   - the provider must then vouch for **that account's own email**
     (`link_email_mismatch` otherwise);
   - an identity already linked to someone else is refused
     (`identity_in_use`).

   Linking never adds a workspace membership: a link is a way to sign in,
   and membership takes an invitation. A user whose address was squatted by
   an unverified sign-up uses the password reset email first, which proves
   the address.
6. Membership is created **only** by first-time provisioning. Leaving or
   being removed from a workspace does three things (Better Auth after-hook
   on `remove-member` and `leave`):
   - the removal is recorded in `sso_removal`, by the person's address and by
     every SSO identity (issuer|subject) they had at the workspace's
     connection;
   - their links to that connection are deleted;
   - when removed (not when leaving) from a workspace that has an SSO
     connection, all their sessions are revoked.

   What a later sign-in gets:
   - with the account still there, an SSO sign-in is an unlinked identity of
     an existing account, refused with `link_required`;
   - after deleting the account, a fresh sign-in (the same identity, or
     another identity with the same address) is not provisioned into the
     workspace: `access_removed`, audited with the reason `removed`.
   An invitation to the address deletes the block. Coming back takes that
   invitation, or a link for an existing account.
7. **Social sign-in never links itself to an SSO-protected account.** Better
   Auth links a GitHub identity to an existing account when GitHub reports
   the same verified email. That is now refused (`account.create.before`,
   `LINK_REQUIRES_SESSION`) unless the request comes from that account's own
   session (Account → Connected accounts) when the account:
   - has an SSO identity, or
   - is a non-owner member of an enabled require-SSO workspace.

   Ordinary accounts keep the existing behaviour.
8. **Cross-tenant**:
   - a connection only provisions into its own workspace;
   - a domain is verified by one connection per instance;
   - links are per connection, so the same `sub` at two workspaces' providers
     (even the same issuer and client) is two identities;
   - a token minted by tenant A's provider fails tenant B's key, issuer and
     audience checks.
9. **MFA**: an SSO sign-in creates the session directly. Montral's TOTP is
   not asked, because the provider's own MFA applies. Linking required
   Montral's full sign-in (2FA included) once.

## Require SSO and break-glass
- With `require_sso` on and the connection enabled, every member **except an
  owner** is held to it. The check happens in two places:
  - **Session creation** (Better Auth `session.create.before`, which every
    method passes: password, GitHub, 2FA verification, email verification,
    SSO). The user's require-SSO workspaces are looked up, and creation is
    refused (`403`, code `SSO_REQUIRED`) unless this session is an SSO
    sign-in through one of those workspaces' own connections.
  - **Every request** (`requireOrg`). A cookie session that opens a
    require-SSO workspace must have been created by that workspace's
    connection (`sso_session` marks SSO sessions). This also covers
    sessions from before the switch, sessions from another method or
    another connection, and members who join later through an invitation.
    The workspace's requirement is cached for 30 s per isolate (forgotten
    at once on the isolate that changed it).
  - **API keys**, also in `requireOrg`. A member's key works on the
    workspace only if it was made from a session this connection created.
    The Better Auth after-hook on `/api-key/create` records that in
    `sso_credential`, per key id. Keys made before the switch, or from
    another sign-in, get `403`. They work again if the requirement is
    lifted. Refusing at use was chosen over deleting them, so turning the
    switch off and on loses nothing.
  - **Agent (OAuth) tokens**, in `requireOrg`, so MCP is covered too. The
    binding is to the token itself, not to (user, client). The OAuth
    provider stamps every access token, refreshed ones included, with
    `sid`, the session that authorized the grant. A member's token counts
    only while `sid` is a live session of this connection (`sso_session`
    joined to `session`, not expired). So:
    - an earlier non-SSO token stays refused even after the same client is
      consented again from an SSO session;
    - signing out of, or expiry of, the authorizing SSO session ends the
      agent's access to the workspace. Re-authorize the agent after the
      next SSO sign-in.
  - **Better Auth's own endpoints**, which do not pass `requireOrg`:
    - **OAuth**: `/oauth2/authorize` (which issues a code by itself when a
      consent is already on file), `/oauth2/continue`, `/oauth2/consent` and
      `/oauth2/update-consent` are refused unless the session satisfies
      **every** require-SSO workspace in which the user is a non-owner
      member. The browser-written picker cookie (`montral_grant`) is not
      used to decide which workspaces a grant covers.
    - **Everything else**: `/organization/*` (invitations, roles, removals,
      set-active, get-full-organization, the member list) and
      `/api-key/create` / `update` follow the per-workspace rule. The
      workspace concerned is the one named in the body or query, by
      `organizationId` **or** `organizationSlug` (resolved server-side; both
      are checked), else the active one.
  - **Issuer or client change** signs out every session the connection
    created and deletes its `sso_credential` rows. Nothing the old provider
    or client vouched for keeps counting.
  - **On the switch** (off to on), sessions of non-owner members that this
    connection did not create are deleted, so those browsers are signed
    out. Until then they are already refused by the checks above. That
    includes Better Auth's 5-minute signed cookie cache of a deleted
    session.
- The **owner is the break-glass account**: they keep password sign-in
  (documented, with advice to enable 2FA), so a provider outage or a broken
  configuration cannot lock the workspace out. Requiring SSO needs at least
  one verified domain (otherwise the flag is saved off, with a warning).
  Disabling the connection lifts the requirement.
- The owner's own sessions, keys and agents are never affected
  (break-glass). The operator's instance-wide provider is another
  connection, so it does not satisfy a workspace's requirement (tested).
- If every verified domain of a require-SSO workspace is withdrawn by the
  re-check, members cannot sign in until the owner restores a record. This
  fails closed on purpose; the owner keeps password access.

## Audit
- `sso.connection_create` and `sso.connection_update`: the field names,
  plus the values of `enabled`, `requireSso` and `defaultRole`.
  `requireSso` and `defaultRole` were added to `SAFE_VALUE_FIELDS`.
- `sso.connection_delete` and `sso.domain_verify` (with the domain).
- `sso.domain_withdrawn`: actor `system`, with the domain and the reason,
  when the periodic re-check withdraws a domain.
- `sso.sign_in`: actor is the user, target is the connection, and
  `changes.values.type` is `provisioned`, `existing` or `linked`.
- `sso.sign_in_refused`: actor is `system`, with `changes.values.reason`
  `email_not_verified`, `domain_not_allowed` or `link_required`. Only
  refusals of an id_token that **passed validation** are recorded, so
  unauthenticated traffic cannot fill the log.
- The instance-wide provider has no workspace, so its sign-ins have no
  workspace audit row.

## SAML: deferred
SAML is not implemented in this change. Reasons:
- **Security risk**: SAML depends on XML Signature, whose canonicalisation,
  reference and multiple-parser handling keeps producing authentication
  bypasses in maintained libraries. Publicly reported examples:
  - xml-crypto CVE-2025-29775 and CVE-2025-29774 (signature bypass, March
    2025);
  - samlify CVE-2025-47949 (signature wrapping, 2025);
  - ruby-saml CVE-2024-45409, CVE-2025-25291 and CVE-2025-25292 (parser
    differentials);
  - @xmldom/xmldom CVE-2022-39353 (multiple roots).

  A login bypass in one of these is a full account takeover. Montral would
  inherit an XML parser plus an XML-DSig stack on its most sensitive path.
- **No safe path on both runtimes**: the maintained Node stacks
  (`@node-saml/node-saml`, samlify with xml-crypto and xmldom) depend on
  Node crypto and DOM shims. Montral's API also runs on Cloudflare Workers.
- **Cost**: SP metadata, certificate rollover, signed and encrypted
  assertions, IdP-initiated flows (an extra replay surface) and per-IdP
  quirks would roughly double the SSO surface, and they need their own
  synthetic IdP and negative-test suite.
- **Demand**: every provider in the request (Keycloak, Authentik, Entra ID,
  Google Workspace, Okta) supports OIDC, as do JumpCloud, OneLogin and ADFS
  2016+. SAML-only cases are mainly older ADFS and academic federations.
  Those can bridge through Keycloak or Authentik (SAML in, OIDC out), at no
  cost.
- **Revisit when**: a paying or self-hosting user needs a SAML-only IdP that
  cannot be bridged. Then evaluate a maintained library that runs on both
  runtimes, with a fuzzing and XSW (XML Signature Wrapping) negative suite
  as a gate.

## Design notes: what is not bound to SSO
- **Owner-made credentials**: API keys and agent authorizations created by
  the owner are not bound to how the owner signs in. The owner is exempt
  from "require SSO" as the break-glass account.
- **Deprovisioning at the identity provider**: credentials made from an SSO
  session survive it until they are revoked in Montral. An API key keeps
  working; an agent token works until its authorizing SSO session ends.
  There is no SCIM. When someone is offboarded, remove them from the
  workspace (which revokes their sessions and blocks re-provisioning) and
  revoke their API keys and agent authorizations.
- **Several require-SSO workspaces**: a member of two require-SSO workspaces
  with different connections cannot authorize agents. The OAuth endpoints
  require the session to satisfy all of them, which one session cannot.

## Domain re-verification
Verified SSO domains keep proving their TXT record (`sso-domains.ts`,
`recheckSsoDomains`), with the status page custom-domain policy
(`DOMAIN_RECHECK`):
- re-checked every 6 hours, and every 30 minutes while failing;
- withdrawn once the record has been missing or wrong for 24 hours over at
  least 3 checks, or DNS has been unreachable for 7 days. A streak that
  switches between the two kinds of failure starts over.

Rows are claimed with `FOR UPDATE SKIP LOCKED`, so several servers share
the work. Where it runs:
- Node: on the existing 5-minute domain re-check timer;
- Workers: on the cron, every 5 minutes, over DNS over HTTPS.

A withdrawal clears `verified_at`, which releases the instance-wide claim
(the partial unique index only covers verified rows). It is audited
(`sso.domain_withdrawn`), and the settings page shows the failure.

## Email verification is strict
`email_verified` must be the boolean `true`. There is deliberately no
per-connection "trust email without the claim" setting: an address the
provider did not verify would let that provider claim any account in the
domain. Other claims are never accepted in its place (`xms_edov`,
`verified_primary_email`, `"True"`; unit-tested).

Entra ID does not send the claim by default. The docs give two ways
instead:
- a claims-mapping policy that emits `true` only for addresses in domains
  verified in the tenant;
- a Keycloak or Authentik broker that asserts it.

## Tests
All tests use synthetic identity providers (`apps/api/test/synthetic-idp.ts`):
an in-process HTTP server on 127.0.0.1 with discovery, a JWKS with rotating
RS256/ES256 keys, an authorize step and a token endpoint. The token endpoint
checks the client secret, the redirect URI and the PKCE verifier, and gives
out single-use codes. Every id_token it issues can be bent (claims,
algorithm, signing key). Nothing external is contacted.

**Unit** (`apps/api/src/sso-oidc.test.ts`, 24 tests, run locally on Windows,
all pass):
- Discovery: happy path; refused for a mismatched issuer, no S256, HMAC or
  `none` algorithms only, no code flow, unsupported client authentication,
  or a non-http JWKS URI.
- Private addresses refused before any request: plain http, 127.0.0.1,
  `localhost`, 169.254.169.254, `[::1]`, `*.internal` and 10/8. They are
  allowed only with `SSO_ALLOW_PRIVATE_IDP`.
- Oversized discovery, JWKS and token responses refused (64 KiB). A slow
  provider is cut off at the deadline. Redirects are refused.
- Issuer input validation (query, credentials, fragment, scheme).
- The authorization request carries code, S256, state, nonce and the
  redirect URI. The code exchange works with the verifier. A wrong verifier,
  a reused code or a wrong secret is refused. `client_secret_post` works.
- id_token refusals:
  - wrong `iss` or `aud`; several audiences without `azp`; wrong `azp`;
  - expired, `iat` in the future, `nbf` in the future, too old, no `exp`;
  - a bad signature (unpublished key under the right kid), `alg: none`,
    HS256 keyed with the public key, an unknown kid, an empty signature or
    garbage;
  - a missing nonce, or another sign-in's nonce.
- Accepted: within the skew; `email_verified` only when literally `true`
  (not `"true"`, `1` or missing).
- Key rotation: a new kid is fetched; a burst of unknown kids within the
  cooldown causes at most one refetch. ES256 keys are accepted.
- The JWKS filter drops `oct` keys, keys with private members and `use: enc`.
- Secret encryption round-trips. It fails closed for another connection id
  (AAD), another server secret, a tampered ciphertext or garbage, and
  refuses a short `BETTER_AUTH_SECRET`.
- With `SSO_ALLOW_PRIVATE_IDP`, these are still refused before any request:
  link-local, metadata (v4, v6, embedded, decimal spelling), multicast,
  broadcast, 0.0.0.0/8 and `::`. The table of `addressAlwaysForbidden`
  (forbidden versus allowed private addresses) is unit-tested.
- Strict `email_verified`: `xms_edov`, `verified_primary_email` and
  `"True"` are never accepted in its place.
- `safeReturnTo` (protocol-relative, backslash and absolute URLs) and
  instance-provider parsing.

**PostgreSQL e2e** (`apps/api/src/sso.e2e.test.ts`, 20 tests, CI only
because there is no local PostgreSQL on the authoring host), with two
synthetic providers (tenant A and tenant B):
- Owner-only management: the secret is never in a response and is
  encrypted in the row. An API key gets 403; a member gets 403. A PUT
  without a secret keeps it.
- Discovery test. With the opt-in off: http is refused, loopback is
  refused, the metadata IP is refused at save, and the provider receives no
  request. A broken issuer is refused.
- JIT provisioning into the connection's workspace only, with the default
  role and a verified email. The authorization request parameters are
  checked. A repeat sign-in is the same user. Sign-out ends the session.
  Audit types `provisioned` and then `existing`.
- Start by workspace slug; 404 `SSO_NOT_CONFIGURED`.
- `email_verified` false, `"true"` or missing is refused. A foreign domain
  is refused. Neither creates a user. Refusals are audited.
- Linking policy:
  - an existing password account is refused (`link_required`) and gets no
    link and no membership;
  - linking without a session is 401;
  - linking from a session works (membership still needs an invitation), and SSO then
    signs in that user;
  - a mismatched email is refused, and so is an identity linked to
    someone else.
- id_token refusals end to end: wrong iss, wrong aud, wrong azp, expired,
  future iat, `none`, HS256, unpublished key, unknown kid. None creates a
  session. A token-endpoint error is an `idp_error`, and its description
  never reaches the logs.
- Replay and binding:
  - a replayed callback (state) is refused;
  - a replayed id_token in a new sign-in (nonce) is refused;
  - another browser's state is refused (with no cookie, and with its own
    binding), and the rightful browser still completes;
  - an expired flow, or a callback with no cookie, is refused;
  - only state hashes are stored.
- Cross-tenant:
  - B's provider returning A's token is refused;
  - A's user through B's connection is refused;
  - B cannot verify A's domain (409);
  - a person provisioned by B is a member of B only and never appears in
    A's log;
  - the same subject at A's provider is refused by domain.
- A disabled connection refuses new starts and in-flight callbacks.
  Re-enabling works.
- Require SSO:
  - the member's password sign-in gets 403 `SSO_REQUIRED`;
  - the member's earlier password session gets 403 on the workspace;
  - SSO works;
  - the owner's password sign-in works (break-glass);
  - turning it off restores password sign-in.
- Audit rows for create, update, domain verify, sign-in and refused
  sign-in. Values are kept for the allowlist only. No secret or id_token
  appears in the audit rows, the API listing or tenant B's log.
- Delete removes the links, the domains and the start route, and is
  audited.
- Review fixes:
  - **Secret binding**: changing the issuer or the client id without the
    secret is a 400 and nothing changes. The token endpoint is pinned: a
    moved endpoint gets `connection_misconfigured` and the provider receives
    no token request.
  - **Social sign-in**: implicit linking of a GitHub account to an
    SSO-provisioned user is refused through Better Auth's own
    `internalAdapter.linkAccount` (and still allowed for an ordinary

  - **Removal is final**: a removed member's link is deleted, the next SSO
    sign-in is `link_required`, and the membership stays gone.
  - **Linking**: linking adds no membership; an invitation does.
  - **Concurrent callbacks** with the same state: exactly one signs in, and
    exactly one session is created.
  - **Require SSO, before the switch**: a password session, an API key and
    an agent (OAuth) authorization are made, and all work.
  - **Require SSO, after the switch**:
    - the session is revoked;
    - `/api/me`, invite-member, update-member-role, API key creation and
      agent consent with it are refused;
    - the earlier key and agent token are refused at use;
    - the role is unchanged.
  - **Require SSO, with an SSO session of the connection**: invite and a new
    key work. An agent for the pre-switch client (consent on file, so the code
    comes straight from `/authorize`) works, while the pre-switch token for
    that client stays refused. After signing out of that SSO session, its
    token is refused.
  - **Require SSO, live non-SSO session** (a member who joined after the
    switch, whose session row still exists): the before-hooks refuse each of

    - set-active by slug and by id;

    - invite-member and API key creation;
    - `/authorize` for a client whose consent is on file;

    Her SSO session's agent keeps working.
  - **Issuer change**: the connection's sessions are signed out, its

  - **Removal and account deletion**: the removed member's sessions are

  - **Require SSO, other connections**: an identity linked to the

  - **Domain re-check**: the record is matched; a first failure starts a

## Not covered / limits
- No interoperability run against real Keycloak, Authentik, Entra ID, Google
  or Okta. The provider settings in the docs are text guidance.
- No userinfo-endpoint fallback: `email` and `email_verified` must be in the
  id_token. Entra ID and some Authentik setups need configuration to send
  them.
- RP-initiated logout (`end_session_endpoint`) is not used. Sign-out ends
  the Montral session only.
- No SCIM or other deprovisioning. Removing a person at the provider stops
  new SSO sign-ins but not existing sessions; removing them from the
  workspace is final.
- One connection per workspace. Multi-tenant issuers (Entra `common`) are
  unsupported.
- Workers: the DNS-over-HTTPS verification path and the SSO flow have not
  run in workerd. Those test files do not start on the Windows authoring
  host, so this is covered by code review only.
- Caches are per isolate: discovery and JWKS for 10 minutes, a workspace's
  requirement for 30 s. Better Auth's signed session cookie cache can serve
  a session for up to 5 minutes after revocation (unchanged behaviour).
- The DB e2e suites could not run locally (no PostgreSQL or Docker on the
  authoring host). They are qualified in GitHub CI.
