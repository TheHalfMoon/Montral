# Probe credential lifecycle: implementation design

## Current implementation boundary

The merged registration inventory persists non-secret region metadata only. PR #220 added a PostgreSQL table for AES-256-GCM envelopes, version/algorithm/key-version metadata, and an append-only audit trail. Preparation accepts envelope bytes from an internal caller, serializes against registration state transitions, and commits the envelope and audit event atomically. The database limits each region to one `prepared` envelope and permits only a `prepared` → `revoked` transition; ciphertext cannot be updated or deleted through ordinary SQL operations. Audit reads return metadata only. PR #221 adds a provider interface that selects an active external KEK version for encryption and resolves the exact recorded version for decryption; it copies key bytes for each operation, clears those copies, sanitizes provider/decryption failures, and persists no KEK. Returned arrays remain owned by the provider, which must define their in-memory lifetime and should return short-lived copies when practical; the provider interface now offers a best-effort release hook after the wrapper has copied returned key bytes, and the file adapter uses it to wipe those bytes. This is an adapter boundary, not a credential-management service. A dormant file-backed provider now reads bounded kek-<version>.bin files plus an active-version pointer, wipes its returned key buffer when the provider wrapper releases it, and fails closed with fixed errors. It is not wired to server startup, routes, delivery, or scheduling. The next read-path slice adds a repository-only accessor for one exact prepared envelope when its region remains registered; it exposes ciphertext and metadata to internal code only.

No operator endpoint, enrollment or delivery flow, credential decryption/delivery service, probe authentication path, or scheduler integration is enabled by these slices. The file adapter accepts immutable 32-byte kek-<version>.bin files and an active-version pointer containing a positive decimal key version; rotation stages a new version file and atomically replaces only the pointer, retaining the old file while persisted envelopes reference it. Operators must keep the directory and key files admin-owned and non-writable by the API, grant the service identity read-only access, and coordinate file backups and replica rollout; the adapter does not enforce these deployment controls. This provider is dormant and has no server startup integration. The repository-only accessor returns one ciphertext envelope for an exact region/version only while the credential is prepared and the registration is still registered; revoked, suspended, unknown, and mismatched versions return null. It performs no decryption, authorization, audit write, or execution and does not resolve the race between a read and a later revocation. A subsequent internal callback helper composes that exact read with exact-version KEK decryption, exposes the plaintext buffer only during a single caller callback, sanitizes failures, and clears the buffer in `finally`. It is not called by an HTTP route, delivery flow, or scheduler, and does not authorize the caller or close the read-to-revocation race; callbacks must remain bounded and future callers must establish fresh authorization and explicit revocation semantics. This helper does not qualify dynamic credential use. The provider wrapper has synthetic tests for key-version selection, missing-key failure, provider-error sanitization, retained-key recovery, and explicit failure after old-key removal. That does not exercise KEK rewrap or restore of a complete database and separately protected KEK backup; file-format tests do not qualify deployed permissions, replica rollout, or recovery. A focused PostgreSQL integration test verifies synthetic envelopes can be persisted and recovered with an externally supplied KEK, and the CI test inspects a real `pg_dump` data-only export to ensure the tested plaintext credential and KEK are absent while ciphertext is present. A new gated synthetic CI restore E2E creates a fresh migrated local database, restores registration metadata, prepared credential envelopes, and both lifecycle audit tables from a custom-format data-only archive, then decrypts the restored exact-version envelope with the separately supplied test KEK. It checks the archive contains ciphertext but not plaintext credentials or the KEK, and that the callback clears its plaintext buffer. The PostgreSQL 17/18 test does not restore the KEK, cover a full application-database snapshot, or qualify deployed recovery, replica rollout, or file permissions. A disposable PostgreSQL 18 integration test now crosses the file-backed provider with persisted envelope preparation and retrieval, switches the active pointer to a new KEK version, and verifies the stored old version still decrypts through the internal callback while its plaintext buffer is wiped. The storage layer still accepts envelope bytes from an internal caller and does not prove that caller-supplied bytes are encrypted. Any future provisioning endpoint must compose generation/encryption and persistence behind one controlled service path and must never accept caller-supplied ciphertext. Prepared and revoked rows retain ciphertext; revocation is a database lifecycle state, not cryptographic erasure. Before credentials are used, qualify KEK rotation/rewrap, stale-backup and restore recovery, bounded overlap, delivery acknowledgement, and replica-wide revocation.

## Decision

### Safe enrollment persistence slice (2026-11-27)

Migration 0068 and an internal API helper now provide a dormant single-use enrollment authorization foundation. The helper generates independent 256-bit CSPRNG token and nonce values, returns their base64url forms once to its immediate internal caller, and persists only SHA-256 digests. The nonce is request-binding material delivered with the token, not an independent authentication factor. PostgreSQL binds each grant to a registered region, the exact stored HTTPS endpoint, one prepared credential version, and a four-minute expiry (the repository rejects expiry beyond five minutes). Only one issued grant per region is permitted. Consume serializes on the same region advisory lock used by registration and credential lifecycle transitions, rechecks registration and credential state, atomically records consumption and a secret-free event, and rejects replay or any token/nonce/region/endpoint/version mismatch. Expiry checks use PostgreSQL `clock_timestamp()` after lock acquisition so lock waits cannot extend a grant. Registration or credential state transitions revoke outstanding grants in the same transaction. Database and audit rows reject mutation/deletion through ordinary SQL paths.

Disposable PostgreSQL 18 tests cover plaintext non-persistence, exact binding, replay, concurrent consumption from separate repository/database pools, expiry, state invalidation, and a consumer waiting on the region lock until after expiry. This slice has no HTTP route, secure channel, probe-side exchange, endpoint resolution or connection pinning, credential decryption/delivery, authentication, activation, or scheduler integration. It therefore does not complete Phase 3 and is not authorization to use managed credentials. Before a future operator-run enrollment path, qualify SSRF and DNS-rebinding protections, bounded transport, independently authenticated delivery, recovery, and the full replica behavior, then obtain the required independent technical review.

Keep the current configuration-managed lifecycle active. Do not enable API-created credentials, dynamic endpoint registration, or secret delivery until the enrollment and replica-revocation boundary below is implemented and qualified. The operator inventory, challenge-response validation, activation/deactivation, and configuration binding already present remain useful controls; they do not provision credentials or attest probe software.

## Ownership and threat boundary

- A platform operator owns region registration and the decision to activate, rotate, or revoke a region. Workspace administrators must never manage platform probe credentials.
- A probe credential authorizes HMAC-authenticated check requests to one configured region. It is not an identity for a human, workspace, customer, or source binary.
- Persistent region metadata is non-secret: stable region ID, display name, endpoint, enabled/deactivated state, credential version IDs, timestamps, operator IDs, and audit state. Secret values, bootstrap tokens, challenge bodies, raw signatures, and URLs must not enter audit records or API responses.
- The API process, its database principal, secret store, probe process, and operator browser are separate trust boundaries. Compromise of the API or its unwrapped key-encryption key can expose all credentials that API can use. Per-region keys limit a single probe compromise; a shared fallback does not.
- Registration must accept only an operator-controlled region identifier and endpoint. It must reject redirects and unsafe schemes, resolve and pin the destination for each connection, deny loopback/link-local/private/metadata ranges unless a separately reviewed self-hosted policy explicitly allows them, and prevent DNS rebinding. Do not accept arbitrary customer URLs.

## Generation and storage

Generate 32 random bytes with the platform CSPRNG (`crypto.randomBytes(32)`), encode only for transport, and assign a random non-secret version ID. Never derive keys from region names, UUIDs, passwords, or `BETTER_AUTH_SECRET`.

| Option | Cost and operation | Decision |
| --- | --- | --- |
| Deployment secret files / Docker secrets / systemd credentials | Zero license cost, self-hostable, supported by the existing environment-based setup. Rotation is operator-managed and coordinated across replicas. | Keep as the current compatible mode and fallback. Prefer file-backed deployment injection over command-line arguments or checked-in `.env` files. |
| PostgreSQL metadata plus application-side envelope encryption | Zero additional service cost and works with existing self-hosted PostgreSQL. Store ciphertext separately from metadata; use AES-256-GCM with a fresh nonce and associated data `(region_id, version_id, purpose)`. The 32-byte KEK must be injected to every API replica as an external secret file and must never be stored in PostgreSQL. | Viable first managed-storage adapter only after backup, KEK rotation, restore, and replica consistency exercises. Database-only backups must not decrypt credentials. Host compromise exposing both DB and KEK remains in scope. |
| OpenBao (self-hosted Vault-compatible secret service) | Zero software license cost, but adds a separately operated service, backup/unseal duties, availability requirements, and API workload authentication. | Optional adapter for operators who already run it; do not make it a required hosted dependency. Do not assume an external paid secret manager. |

Persistent registration metadata belongs in PostgreSQL. Secret-bearing credential versions belong in an encrypted credential table or a configured secret provider, never in the region metadata row, logs, audit trail, or list/read API. Do not persist plaintext as an expedient. If the external KEK is missing or decryption fails, fail closed for the affected region and expose only a fixed operator error.

## Enrollment and delivery

The current model is manual out-of-band provisioning: deploy `PROBE_SECRET` to the probe and the matching `PROBE_SECRETS` value to the API. Retain it for compatibility. A future dynamic flow must not return a long-lived secret to the browser or place it in an audit record. Prefer a short-lived, single-use bootstrap exchange authenticated by a separately established channel (mTLS client certificate or an operator-run local enrollment command with a one-time token). Bind the exchange to region ID, endpoint, key version, nonce, and expiry; store only a hash of the one-time token; consume it atomically; refuse replay. A shared one-time bearer copied through ordinary UI or logs is not an acceptable replacement for secure provisioning.

Every later request remains HTTPS-only with redirects disabled and bounded timeouts/body sizes. HMAC input must bind method, exact path, body hash, region ID, key version, timestamp, and nonce; the probe must enforce a replay window and compare signatures in constant time. Do not send monitor target data during credential possession validation.

## Rotation, revocation, and replica behavior

Allow at most one previous credential version. Rotation is: create new version; provision it to the probe out-of-band or via the qualified enrollment channel; validate possession against that exact version and endpoint; atomically make it primary while accepting the previous version for a hard maximum of 15 minutes; wait for bounded in-flight requests; then remove the old version. The probe and API must both enforce expiry. Extending overlap requires a new audited rotation, not an indefinite grace period.

Revocation is an atomic PostgreSQL state transition plus append-only audit and an outbox/version bump. Every API replica must check current credential state before signing; a bounded cache must have an explicit short TTL (maximum 15 seconds, matching the existing lifecycle-state cache). Database/outbox read failure denies new signatures and registrations. A replica that cannot observe revocation within that bound is not qualified. Revocation cannot cancel an already-sent network request; bound its duration and record that limitation. Do not restore a revoked key by rolling application code back; recovery requires a new version and fresh proof.

## Audit, failure, recovery, and compatibility

Audit only region ID, operator ID, action, fixed outcome, key version ID, and time. Make audit append-only, commit it with lifecycle state, and fail the operation if audit persistence fails. Never include the secret, encrypted ciphertext, KEK fingerprint, full URL, raw probe response, challenge, or signature.

Backups of encrypted credential rows are useful only with a separately protected KEK backup. Restore rehearsal must prove old revoked versions remain revoked and that active credentials can be revalidated. If the KEK is lost, do not attempt plaintext recovery: provision new synthetic/test keys, invalidate old versions, and perform a fresh activation proof. Rollback must preserve schema compatibility and must not re-enable a revoked key or accept a previous key past its expiry.

Existing `PROBE_REGIONS`, per-region `PROBE_SECRETS`, shared `PROBE_SECRET` fallback, and probe-side expiring previous-key support remain readable during any future migration. A dynamic record must not silently override an environment-configured endpoint or credential. Require an explicit conflict error and staged operator migration; keep current configured probes enabled by default until their operator deliberately adopts managed registration.

## Safe next implementation gates

Before enabling any dynamic credential endpoint, require synthetic-only tests for malformed/duplicate region IDs, SSRF and DNS rebinding, one-time token replay, cross-region and cross-tenant authorization, secret non-disclosure, concurrent rotation, expiry boundaries, revocation visibility on multiple replicas, DB outage fail-closed behavior, append-only audit rollback, restore/rollback, and existing configuration compatibility. Run these against disposable PostgreSQL and simulated probes; test keys only. Until these pass and receive an independent technical review, retain the existing static configuration path and do not activate managed credentials.

## Bootstrap grant trust decision (2026-11-28)

The receiver must authenticate the control plane independently of TLS server authentication. The selected protocol direction is an API-signed, short-lived grant verified with an Ed25519 public key pinned in probe configuration. The signature binds protocol version, signing-key ID, grant ID, region, exact registered HTTPS endpoint, purpose, credential version, nonce, issue time, and expiry. The signature is public authorization metadata, not a credential; the private signing key must remain external to the probe and must not be stored in PostgreSQL. TLS hostname verification remains required to authenticate the registered probe endpoint. Grant signature verification does not attest the probe binary, source, or deployment.

The Node probe now has an opt-in enrollment receiver that requires an injected encrypted store, pinned API public key, exact region/endpoint, and a TLS key/certificate. It checks the actual TLS socket and rejects a plaintext connection; it does not trust forwarded-proto headers. The repository's default probe startup supplies none of this configuration, so the receiver remains inaccessible in the default application. Synthetic local HTTPS tests exercise a signed grant, durable credential staging, post-persistence HMAC proof, and an identical-request retry; they do not qualify deployment TLS, API-side DNS resolution/pinning, or network/API integration.

PR #233 merged after 23/23 exact-head checks and an independent receiver review; all 12 required exact-main push workflows passed on the verified main commit recorded in the repository history. It added a dormant Node HTTPS receiver. The follow-up delivery slice adds an opt-in operator API path, encrypted credential preparation, Ed25519-signed grants, persistent exact-envelope retries, guarded HTTPS delivery, proof verification, and transactional PostgreSQL settlement to `verified`. The persisted signed envelope includes the public nonce in its claims so retries can reproduce the same request; PostgreSQL stores only the bootstrap token digest, and neither the nonce nor the signed grant is treated as a secret or independent authentication factor. No plaintext credential is returned to the browser or written to audit events. A real TLS receiver plus disposable PostgreSQL test now exercises the API-to-probe path, response loss after receiver persistence, byte-identical retry, SQLite persistence, and one-time settlement. Its DNS answer and socket dispatch are controlled by the test harness; DNS rebinding and pinned TCP behavior remain covered by separate netguard tests, not this end-to-end test.

These changes still do not activate the credential for monitoring. The receiver stages it as `prepared`; PostgreSQL records `verified` only after proof and a fresh registration/credential check. The default probe startup does not mount the receiver, and API delivery remains unavailable unless the operator explicitly configures the KEK directory and Ed25519 signing key. A signer key-ID rotation while a grant is pending can make it unretryable until its four-minute expiry; a later attempt can then issue a fresh grant. A suspension or revocation racing an in-flight POST may leave an inactive prepared credential on the probe, while transactional settlement refuses to mark it verified. Dynamic runtime activation, rotation overlap, replica-wide revocation, cleanup of orphaned staged credentials, restoration behavior, operator UI lifecycle controls, and multi-replica runtime qualification remain open. The existing environment-based path is still the only active authentication path.
