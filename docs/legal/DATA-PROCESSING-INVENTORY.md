# Engineering data-processing inventory for legal review

**Status:** preliminary engineering fact-finding; not a privacy notice, DPA, legal opinion, or approval to launch. Prepared 2026-11-21 from repository source at `main@68814c606a1cf6f7f561f0b7ca18585a7f885a49`.

## Scope and limits

This inventory describes data structures and integrations visible in the Montral source tree. It does not establish which optional features are enabled in any installation, what data a real operator has collected, the behavior or retention of a hosting provider, or whether a hosted service is operating. Community is self-hosted: the person or organization running an instance chooses its database, network, mail, identity, backup, logging, and notification providers and is responsible for its operations. Montral Cloud is not publicly available. No hosted customer processing or production practices are verified by this document.

The schema and code are an engineering inventory, not a complete field-by-field data-flow audit. Qualified privacy counsel and the future service operator must validate purpose, lawful basis, roles, notices, rights handling, transfers, subprocessors, security measures, retention, deletion, and incident duties before any hosted launch.

## External systems and disclosures to verify

The source supports optional integrations with GitHub OAuth, OIDC identity providers, SMTP/Resend or Cloudflare Email, APNs, and configured alert destinations such as Slack, Telegram, PagerDuty, webhooks, and other listed channels. Monitor checks and browser journeys make requests to user-configured targets; domain-expiry lookup uses public RDAP bootstrap/registry services. Deployments may also use PostgreSQL, Cloudflare Hyperdrive/Queues/Email, a browser-runner service, and remote probe endpoints. This list is based on integration points, not a verified production vendor/subprocessor list.

Before hosted processing, the operator must produce the actual infrastructure and subprocessor register, data-region/transfer map, request/response logging configuration, backup and disaster-recovery retention, email and alert-provider terms, identity-provider scopes, telemetry/analytics inventory, support-access procedure, and deletion propagation evidence. Repository review alone cannot answer these operational questions.

## Questions for qualified privacy counsel and the service owner

1. Identify the legal entities and roles for Community (self-hosted operator) and any future hosted service; confirm controller/processor responsibilities per data flow.
2. Approve purposes, lawful bases, categories of people/data, data minimization, privacy notices, cookies/storage, and data-subject request handling for a real hosted product.
3. Confirm the actual subprocessor list, locations, international transfer mechanism, support access, and contractual commitments before Cloud is offered.
4. Set and implement retention/deletion schedules for accounts, monitor history, incidents, subscriber contacts, logs, audit records, billing records, backups, and provider copies; document exceptions and legal holds.
5. Validate credential handling and lifecycle for OAuth tokens, API keys, monitor headers/secrets, SSO secrets, push tokens, email/channel destinations, and recovery data.
6. Decide whether and how optional hosted billing, analytics, support tooling, and incident telemetry will operate; verify each production flag and provider account independently.
7. Review the bundled `/terms` and `/privacy` drafts. They remain unapproved and not in force; this inventory does not make them binding or complete.
